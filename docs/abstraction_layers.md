# Уровни абстракции (MVP)

Этот документ описывает ключевые слои pet-проекта и их тестирование.

---

## UI Tree Layer (`src/ui_tree`)

Назначение:

- представить UI приложения в виде иерархии логических нод;
- отделить работу с координатами и геометрией от бизнес-логики;
- обеспечить единый интерфейс для UI-моделей и действий.

### Автоматизационные идентификаторы

Для устойчивости и читаемости автотестов желательно, чтобы разработчики приложения
помечали значимые элементы явными автоматизационными идентификаторами
(test id / automation id / accessibility id и т.п.).

В MVP такие идентификаторы хранятся в атрибутах нод (`attributes["test_id"]`),
а модели и actions в первую очередь опираются на них при поиске элементов.

### Бэкенды представления UI

- Основной источник данных — внутреннее логическое дерево элементов (в MVP — JSON-snapshot в `config/ui_tree`).
- Для экранов/окон, где такое дерево недоступно, в реальном фреймворке возможен второй тип бэкенда
  поверх дерева элементов драйвера (accessibility / native UI tree).

### Контракт слоя

- предоставляет стабильные абстракции `Node` и `Bounds` для верхних слоёв;
- гарантирует корректную работу навигации по дереву и вычисление геометрии элементов;
- не знает о бизнес-сценариях, тестах и конфигурации запуска.

### Тестирование слоя

Unit-тесты:

- `test_ui_tree_node.py` — структура дерева, ссылки родитель/дети, поиск по предикату;
- `test_driver_bridge.py` — пересчёт bounds в координаты точки касания.

## Input Layer (`framework/input_layer`)

Назначение:

- исполнять жесты поверх драйвера, используя координаты экрана;
- отделить жесты от конкретной реализации драйвера.

Контракт:

- принимает либо логические bounds (через `tap_bounds`), либо уже готовые координаты (`tap_point`);
- использует `driver_bridge` для пересчёта логических координат в экранные;
- вызывает методы драйвера (`tap`, `swipe` и т.п.).

Тестирование:

- в MVP — косвенно через feature-тест:
  - action вызывает модель;
  - модель находит элемент в `ui_tree`;
  - input layer исполняет жест;
  - `FakeDriver` записывает вызов, который проверяется в тесте.

---

## Framework Layer (`framework/*`)

Содержит:

- `driver` — протокол драйвера и `FakeDriver`, записывающий историю вызовов;
- `launch` — сборка `LaunchConfig` и `SessionContext`;
- `session` — описание контекста сессии;
- `input_layer` — слой ввода (см. выше).

Тестирование:

- unit-тесты могут проверять:
  - корректную сборку `LaunchConfig` из конфигов и CLI;
  - корректную сборку `SessionContext` (наличие driver/ui_tree/input/config);
- интеграционно — через feature-тесты.

---

## Unit Layer (общий принцип)

Unit-тесты в MVP:

- запускаются отдельно (`pytest src/tests/unit`);
- не требуют реального драйвера или приложения;
- проверяют логику `ui_tree` и `driver_bridge`.

В реальном фреймворке этот слой расширяется на валидаторы, утилиты и API-клиенты.
